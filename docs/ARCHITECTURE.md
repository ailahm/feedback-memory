# 架构与处理规则

## 一条反馈的生命周期

1. `prepare` 检查格式、请求指纹、记忆版本与反馈修订号。重复请求返回已有任务；同键不同内容或版本冲突报错。在事务中保存表态，失效关联旧 pending 提案，持久化任务与当前记忆快照。
2. `run_job` 调用提取器，失败时保留表态并把任务标为 retryable。已完成任务复用结果。
3. `checked_units` 校验分类和字段，验证证据是请求内用户消息的连续片段。助手消息不能充当用户事实。
4. `finish` 在事务中再次检查反馈与记忆版本，过期结果标为 stale，不写记忆。有效语义单元逐条仲裁；同一提取内同键的矛盾取值先转为待澄清。
5. `apply_memory` 保留旧记录并标记 superseded，建立双向修订关联。一次事务内的记忆变化统一递增整体版本。

## 提案与记忆分开

提案带有来源消息、方向、属性、取值、情境、明确程度和仲裁动作。方向包括 self、supply、demand、boundary。比较键为 `(direction, attribute_key, scope)`，取值相同视为重复；取值不同需要判断是否为明确纠正。

| 条件（按仲裁优先级） | 动作 |
|---|---|
| 相同方向、属性、情境存在使用禁令 | no_change / rejected |
| 本次表达自相矛盾或不明确 | clarify / pending |
| 与当前有效记录取值相同 | no_change |
| 新的硬边界 | clarify / pending |
| 与旧记忆冲突，但未明确纠正 | clarify / pending |
| 明确纠正 | update / applied |
| 新的明确软偏好 | add / applied |

单人评价、临时状态和呈现问题仅返回分类，不产生长期偏好。unclear 设置澄清需求。非法单元被排除并返回 validation_errors；同批合法单元仍可能采用，不是整批全部拒绝。

## 确认与权限

`confirm` 检查用户归属、提案状态、记忆版本、反馈版本及使用禁令。接受后采用提案，拒绝后仅改变提案状态。`active` 表示有效；`confirmed` 表示是否经过额外显式确认，两者含义不同。

新明确软偏好自动采用是实验规则，不能直接当作生产授权依据。首次采用默认 self=true、matching=true、public=false，修订继承已有权限。

`revoke` 禁止同键记忆及派生修订继续使用，并失效相关待采用提案。当前不提供自动重新授权；禁令范围较保守，未来需要结合业务确定是否细化到取值或具体证据。

## 恢复与边界

持久任务支持显式 retry，不包含常驻调度器。stale 任务不会自动用新版本重算，需要重新读取状态后提交新的请求。重复请求返回首次结果快照；最新状态通过 state 查询。

原话片段验证不能证明语义正确；certainty 和 correction 仍依赖提取器判断。本地提取器是有限规则，模型适配器尚未做在线验证。

## 设计取舍

- 多含义提取保留一句话中的独立表达，但要检测同批矛盾，避免按顺序相互覆盖。
- 反馈修订号和记忆版本分别保护表态撤改与记忆纠正，代价是无关版本更新也会使任务过期。
- 对“证据存在”和“证据支持结论”分别验收，避免引用通过率掩盖语义错误。
- 保留不修改的结果及原因，使正确拒绝写入也能被评测。
